# Dungeon Run shared draft catalog

Generated by `tools/dungeon-run-catalog` (`dotnet run -c Release`); do not edit by hand. The catalog itself is
`data/dungeon-run/catalog-v1.json`, embedded in the plugin and loaded by `DungeonRunData.Parse`.

It holds the 52 fixed SoloStone bundles of `pool-v1.json` (`draw: fixed`, `legacy: true`, offered to legacy runs)
and one pool entry per original adventure bucket (`draw: pool`): three cards drawn from the admitted members.
Each member was admitted with the run layer's own predicate, in this order (the first failure is recorded):
`engine:missing`, `engine:unscripted`, `admission:<family>` (`DungeonRunAdmission.Classify`, player scope, catalog run),
`validator:<check>` (`DungeonRunValidator.PoolCardReason` with the entry's class set; a grant passes the class
check), `rune-cost`, then `curation:<note>`. A member is tried as its listed id, then each reprint alternate in order;
the first id that passes is the one drawn (`id`), and `wikiId` keeps the listed id. The game drops a candidate its
client does not know at load (`catalog: <entry> dropped <id> client-unknown` in the log) and withdraws an entry left
with fewer than 3; the catalog marks every card `clientChecked: false` for that reason.

## Unreachable entries

Offerable entries that no playable class row can be offered (`unreachable` in the catalog). A Tombs of Terror
entry needs a run with both its classes (`requires.classesAll`); a class row that ships disabled in `run-v1.json`
(`catalogClasses`, `enabled: false`, with its `disabledReason`) leaves its entries in the catalog, counted apart
(`reachableOfferablePoolEntries`, `admittedReferencesReachable`). Since phase 6 F10 every dual row ships enabled.

None.

## Merges

Entries merge only when they differ in nothing but their hero and provenance: the same adventure, label, class set,
requirements, distinct flag, quest, themes and admitted members (grants included).

None.
