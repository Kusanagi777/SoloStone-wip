### Admission families

`ai_support` for Secrets and deck-dependent cards comes from the admission table in `plugin/DungeonRun/DungeonRunAdmission.cs`, the same table the validator applies to pool cards, player and legacy powers, active treasures and their tokens, passive treasures and their effects, run content shells (shrines included), boss decks and boss powers, and the engine applies to generated cards over the whole card pool (`RunMatchPlan.ExcludedGenerated` for both sides, `ExcludedGeneratedBoss` for the boss's generation only). A card is a subject when it is a Secret, has tag 997 or a sideboard, has a Secret or deck phrase in its text, or is listed; a subject with no rule is rejected as `unclassified`. Scopes: player (run player cards), boss (boss decks and powers), generated (Discover and random cards in a run match). A lift names the numbered goal phase that owns the work; a lift starting `none:` names no pending work: nothing in the five adventures needs that scope. A rule with a pending requirement admits no scope until its lift.

## Classification rules

Four criteria, each from its own column:

- **engine**: `engine_behavior` is scripted or vanilla-no-script-needed (catalog containers count as behaving). For heroes (playable or boss) the portrait is not the content: the criterion holds only when a current loadout or encounter uses it.
- **reach**: for every kind of role the row has. A player role (bucket member, starter, finale deck, hero, hero power, treasures, shrine, teammate, anomaly, twist, tavern) needs `player_availability` offered; an encounter role (boss hero, boss power, boss card, boss deck) needs `encounter_use` used. An original bucket card that only appears in a SoloStone boss deck is therefore not reached. Rows with only neutral roles (adventure card, token) need either.
- **ai**: `ai_support` is ok or ok:<family> (the admission table admits the card for the row's roles; an unscripted admitted card keeps its engine gap).
- **validation**: `validation` passes or is not applicable.

Then, in order:

1. **duplicate/support**: portraits and variants, Heroic-mode power variants, enchantments, dummies, tokens and shrine board forms, bucket labels, legacy save-only content and run effects. Dependencies, not rewards; `owner` links the owning record.
2. **implemented**: all four criteria hold.
3. **intentionally adapted**: an exact SoloStone analogue covers the original (`adapted_by`).
4. **partial**: a partial analogue exists, or at least one of engine/reach holds but not all four criteria.
5. **missing**: neither engine nor reach holds: original gameplay content that neither behaves nor appears.

## How the ledger is updated

The ledger is generated, never hand-edited. Every later phase (Secret-aware AI, the draft catalog import, loadouts, treasures, shrines, encounters, global rules) changes the engine, the run data or the validator, and then re-runs the generator:

```sh
cd tools/restoration-ledger
dotnet run -c Release
```

It builds the engine (`engine/SabberStoneCore`, net10.0) and compiles `plugin/DungeonRun/DungeonRunData.cs`, `DungeonRunValidator.cs`, `DungeonRunAdmission.cs` and `plugin/Npc/World/NpcWorldJson.cs` unchanged, so availability and admission are exactly what the run layer would decide. Then:

1. Review the diff of `restoration-ledger.csv` and of the counts here; a phase is done when its rows move to *implemented* (or to *intentionally adapted* with a cited analogue).
2. A new admission rule (Secrets, deck-dependent cards) goes into `plugin/DungeonRun/DungeonRunAdmission.cs`; a new analogue or treasure-name fact goes into `tools/restoration-ledger/curation.json`; never into the CSV.
3. New reference inputs (bucket members, reconstructed boss decks) go under `data/dungeon-run/reference/`; the generator reads them by path.
4. When a phase adds a new kind of content or admission rule (board shrines, anomalies, boss-deck import), extend the role or validation mapping in `Program.cs` so those rows stop reading *not applicable*.
